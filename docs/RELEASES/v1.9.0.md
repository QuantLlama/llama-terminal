# Release notes — v1.9.0

**Cloud mode.** The platform can now run as a web application on a server while the trading
terminal stays on your machine. Same interface, same backend, no install for the person using
it — and MetaTrader 5 still does the trading.

Live deployment: <https://llama.nbmsystemas.com>

---

## Highlights

### The terminal is now usable from anywhere

A container image ships the web/API surface: FastAPI, the SPA, the WebSocket streams, the
service layer and the broker abstraction. Traefik terminates TLS, three volumes hold state, and
the image runs as a non-root user with a health check.

- A browser is enough. No Electron, no Python, no broker terminal on the client.
- The desktop build is unchanged and still the full experience.
- Hardware requirements are modest: the reference deployment runs on 2 vCPU / 3.7 GB.

Read [`../CLOUD.md`](../CLOUD.md) for the topology, request paths, security model and operations.

### MetaTrader 5 over an authenticated bridge

`MetaTrader5` is a Windows-only package that attaches to a local terminal, so it cannot run in a
Linux container. The platform now reaches it over HTTP:

- `mt5_server.py` exposes the venue with gzip compression and an `X-Bridge-Token` requirement.
- It refuses to serve a non-loopback bind without a token.
- The container reaches it through a host relay and a private tailnet — never a public port.

That is the change that makes the cloud deployment possible at all. The security reasoning is in
[`../adr/0001-mt5-behind-an-http-bridge.md`](../adr/0001-mt5-behind-an-http-bridge.md).

### Symptom → cause → fix

The eight integration failures that shaped this release — unreachable tailnet addresses, a
symbol catalogue that stalled charts, a regional `HTTP 451`, keys that could not be written,
vendored assets missing from the image — are documented with their commit references in
[`../CLOUD.md`](../CLOUD.md#8-integration-problems-cause-and-fix).

## New

- **Container image** — `python:3.11-slim`, non-root (`uid 10001`), `/health` check, volumes for
  configuration, outputs and logs, optional CPU-torch build arg.
- **Coolify deployment** — Traefik in front, Dockerfile build, read-only deploy key, documented
  resource identifiers and verification commands.
- **MT5 bridge** — token middleware, gzip, shared session reuse, lazy reconnect, symbol catalogue
  served and cached.
- **VPS relays** — `deploy/vps/setup-mt5-relay.sh` and `setup-crypto-proxy-relay.sh` install
  `socat` relays firewalled to the Docker subnet, because Tailscale drops tailnet traffic arriving
  from a non-tailnet interface.
- **Crypto egress proxy** — `CRYPTO_HTTP_PROXY` routes CCXT traffic through a CONNECT proxy on the
  operator machine, for venues that block the server's region.
- **Local services** — systemd user units for the bridge and the proxy, so they survive reboots.
- **SQLite workspaces** — named workspaces with cross-timeframe drawing state.
- **Liquidity heatmap** — crypto liquidity visualization with an optimized overlay renderer.
- **Order-flow overlays** — large-trade overlays that realign on timeframe change and resize.

## Changed

- MT5 market data is served through the connector abstraction instead of direct package calls in
  the API layer.
- Symbol catalogues are filtered server-side and cached locally instead of being re-downloaded.
- The SPA no longer serves itself as the favicon.

## Fixed

- Bridge calls carry the token on every request and reject error payloads instead of returning
  them as data.
- A single request no longer tears down the shared bridge session.
- Bridge symbols whose `trade_mode` is unknown are listed instead of silently dropped.
- The bridge starts under Wine using the Windows Python inside the prefix.
- Credential keys can be written to a mounted volume (`QUANTUM_LLAMA_KEY_DIR`), and the runtime
  user can write the application tree.
- Vendored web libraries and images ship in the image.
- CFD session detection and MT5 tick restoration after the weekend gap.
- Real-time MT5 ECN candle rendering and timezone synchronization.
- `sqlite3.Row` attribute error on the workspaces query; workspaces refresh on platform change.
- Drawings no longer swallow clicks on the price and time axes, restoring zoom.

## Upgrade notes

1. **Remote bridge users:** the bridge now requires `MT5_BRIDGE_TOKEN`. Set the same value on the
   bridge and on the application, then restart both. Loopback-only desktop use is unchanged.
2. **Containers:** set `QUANTUM_LLAMA_KEY_DIR` to a writable path (the documented value is
   `/app/config/keys`) or credential storage fails on a read-only project root.
3. **Regions with exchange blocks:** set `CRYPTO_HTTP_PROXY` to the relay address; only crypto
   traffic uses it.
4. **Coolify:** point `MT5_BRIDGE_URL` at the relay (`http://10.0.0.1:8081`), never at a tailnet
   address — the container has no route to it.
5. **Back up the `qllama-config` volume** before changing account or workspace configuration.

No configuration format changed and no data migration is required.

## Known issues carried into this release

- The API's platform version constant still reports `2.4.0` while the product is `1.9.0` (#8).
- The desktop readiness probe targets a route that does not exist; the SPA fallback answers it
  with HTML (#1).
- Live inference assumes a 7-feature input while training produces 8 (#2).
- Stale `.so` files from a local obfuscation build shadow the sources on Python 3.11 (#14).

Full list and status: <https://github.com/QuantLlama/llama-terminal/issues>.
