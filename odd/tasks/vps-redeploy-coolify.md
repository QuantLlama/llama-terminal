- L16: Root cause of "API connect error: timed out" (delegated read-only diagnosis): the app login is NOT the problem, and the credential decryption is NOT the problem either. The MT5 bridge on the operator machine runs **without `DISPLAY`** (uvicorn pid 836 env has none, despite the unit using `PassEnvironment=DISPLAY XAUTHORITY`), so Wine cannot create a window (`err:winediag:nodrv_CreateWindow`) → `mt5.initialize()` fails with IPC send/recv errors 101 times since 23:10 → `terminal64.exe` crash-loops. Worse, `mt5_server.py:43-50` runs the blocking `ensure_connected`/`mt5.initialize(timeout=2000)` directly on the async event loop, so each failed attempt (~6s) queues every request: `/api/terminal/status` answered in 7.096s while `/health` and `/api/connect` timed out; the client (`mt5_api_connector.py:145`, `httpx.Timeout(10.0, connect=5.0)`) then reports the timeout. The relay and network are exonerated: from the container, TCP connect to 10.0.1.1:8081 took 0.000830s. Secondary: the demand-lease TTL is 120s (`mt5_terminal_demand.py:23`) but the app renews every 130-148s, leaving 503 windows. Fixes: (a) operational, needs operator consent because it writes outside the repo and restarts their bridge: set `Environment=DISPLAY=:0` (and XAUTHORITY) in `deploy/local/qllama-mt5-bridge.service`, reinstall the runtime unit, restart; (b) code robustness: `await asyncio.to_thread(ensure_connected, connector)` in `mt5_server.py`; (c) lease TTL ≥ 180s or renewal < 60s.
